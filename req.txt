### 1. Executive Summary
The current NeerMitra system possesses a robust and functional ETL data pipeline (successfully pushing data to Backblaze B2/SQLite) and a beautifully designed frontend. However, the NLP and Agent layer (`nlp/orca_service.py` and `agents/orchestrator/graph.py`) relies heavily on rigid, regex-based keyword matching (e.g., Hinglish/Manglish dictionaries) and hardcoded mock data fallbacks (e.g., `random.uniform()` in `ocean_agent.py`). It acts as a text synthesizer rather than a true cognitive engine. Transforming this into a genuine, data-driven AI requires shifting to a structured LLM-parser that retrieves real data, applies deterministic safety thresholds, and generates conditional responses without inventing data.

### 2. Existing Architecture
*   **Frontend:** React (Vite) dashboard (`HomeDashboard.tsx`, `MarineMap.tsx`).
*   **Backend:** FastAPI/Uvicorn (`server/src/controllers/chat_controller.py`).
*   **Agent Orchestrator:** LangGraph state machine (`agents/orchestrator/graph.py`).
*   **NLP Pipeline:** `nlp/orca_service.py` uses predefined regex to detect language, translates to English, does keyword-based intent classification, pulls static RAG context, and synthesizes an answer.
*   **Data Pipeline:** Automated ETL schedulers (`pipeline_runner.py`) actively pushing Copernicus, GEE, NOAA, INCOIS, and IMD data to B2/SQLite.

### 3. Current NLP Pipeline Assessment
The current pipeline violates the core goal of a "data-driven NLP system" in several ways:
1.  **Hardcoded Intents:** `detect_alert_type` and `detect_hinglish` use static word lists.
2.  **Invented Data:** `ocean_agent.py` contains a try-except block that explicitly falls back to `random.uniform()` to invent SST, Chlorophyll, and PFZ scores if B2 fetches fail. 
3.  **Static Isolation:** The NLP service (`orca_service.py`) operates largely independently of the dynamic LangGraph swarm (`run_marine_agent`), leading to a disjointed flow.

### 4. What the Intended Architecture Requires
1.  **Stage 1 (Query Understanding):** An LLM must replace the regex dictionaries to output a structured JSON plan (Intent, Entities, Required Parameters, Language).
2.  **Stage 2 (Actual Data Retrieval):** Agents must strictly fetch from B2 or the database using the query plan, failing gracefully if data is missing, rather than generating random numbers.
3.  **Stage 3 (Conditional Analysis):** A strictly deterministic, non-LLM Python module must calculate risk levels based on INCOIS/IMD thresholds (e.g., Wave > 2.5m = DANGER). LLMs should never calculate safety limits.
4.  **Stage 4 (Conditional Response Generation):** The LLM receives the deterministic safety conclusion + the actual data, and generates a fisherman-friendly response strictly anchored to that context.

### 15. Conditional Analysis Requirements
*   **Fishing suitability:** Requires Wave < 1.5m, Wind < 15kts, NO active IMD alerts. If true, evaluate PFZ score.
*   **Rough sea conditions / Strong wind:** Wave >= 1.5m OR Wind >= 15kts -> `CAUTION`. Wave >= 2.5m OR Wind >= 25kts -> `DANGER`.
*   **Outdated/Missing Data:** If timestamp > 24 hours old, the system **must** append a warning: *"Data is outdated. Proceed with caution."* If data is missing entirely, system **must** refuse to give a safety clearance.
